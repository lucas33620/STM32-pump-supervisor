# Requierements

## Functional Requirements

| ID     | Requirement                                                                                                         | Priority | Acceptance Criteria                                                                                                                                                                                                  |
| ------ | ------------------------------------------------------------------------------------------------------------------- | -------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| FR-001 | The system shall initialize all required hardware peripherals and software services at startup.                     | High     | After power-up, the system reaches INIT complete state, all required tasks are created, and periodic diagnostic communication is started.                                                                            |
| FR-002 | The system shall identify the reset cause at boot.                                                                  | High     | After startup, the reset cause is stored internally and made available in at least one diagnostic message or snapshot response.                                                                                      |
| FR-003 | The system shall periodically acquire temperature data from the primary sensor.                                     | High     | During nominal operation, one temperature acquisition is performed every 100 ms ± 10 ms.                                                                                                                             |
| FR-004 | The system shall detect sensor communication failure or timeout.                                                    | High     | If 3 consecutive sensor acquisition cycles fail, a sensor communication fault is raised within 300 ms and reported on CAN within the next 500 ms.                                                                    |
| FR-005 | The system shall detect invalid or out-of-range temperature values.                                                 | Medium   | If a temperature value is below -20°C or above +100°C for 2 consecutive acquisitions, the corresponding fault is raised.                                                                                             |
| FR-006 | The system shall control the pump or equivalent actuator according to temperature threshold rules.                  | High     | When temperature rises above the activation threshold, the actuator command changes to ON within 100 ms. When temperature falls below the deactivation threshold, the actuator command changes to OFF within 100 ms. |
| FR-007 | The system shall apply hysteresis to actuator control to avoid rapid switching.                                     | Medium   | With a temperature oscillating within ±1°C around the switching threshold, the actuator state shall not toggle more than once within 5 s unless a hysteresis boundary is actually crossed.                           |
| FR-008 | The system shall transmit a periodic heartbeat message over CAN.                                                    | High     | One heartbeat CAN frame is transmitted every 500 ms ± 50 ms during INIT, NORMAL, and DEGRADED modes.                                                                                                                 |
| FR-009 | The system shall transmit periodic system and thermal status over CAN.                                              | High     | At least one status CAN frame containing system mode, actuator state, and current temperature is transmitted every 500 ms ± 50 ms during operation.                                                                  |
| FR-010 | The system shall receive and process diagnostic commands over CAN.                                                  | High     | For any valid diagnostic command received, the system applies the requested action within 200 ms and makes the resulting state observable through CAN.                                                               |
| FR-011 | The system shall reject invalid or unsupported diagnostic commands.                                                 | Medium   | For any invalid command frame, the system shall not change actuator state, shall increment an invalid diagnostic command counter, and shall remain operational.                                                      |
| FR-012 | The system shall detect and report selected faults through the fault management service.                            | High     | For each supported injected or detected fault, a fault entry with ID, state, and severity is available internally within 200 ms and reported over CAN within 500 ms.                                                 |
| FR-013 | The system shall enter degraded mode when a configured critical fault is active.                                    | High     | When a critical fault is raised, the system enters DEGRADED mode within 200 ms and applies the configured safe actuator behavior within 100 ms after mode transition.                                                |
| FR-014 | The system shall supervise the health of critical FreeRTOS tasks.                                                   | High     | Each critical task shall update a heartbeat at least once every 200 ms. If one heartbeat is missing for more than 400 ms, a supervision fault is raised within the next 200 ms.                                      |
| FR-015 | The system shall refresh the watchdog only when critical supervision conditions are satisfied.                      | High     | If a critical supervision condition fails for 2 consecutive supervision cycles, watchdog refresh is inhibited within 400 ms according to policy.                                                                     |
| FR-016 | The system shall remain diagnostically observable during degraded operation and support DiagPack CAN bench testing. | High     | In DEGRADED mode, heartbeat and fault/status CAN frames continue to be emitted while the system remains powered and operational, and at least 3 predefined DiagPack CAN test scenarios are executable end-to-end.    |

## Non-Functional Requirements

| ID      | Requirement                                                                                                                            | Priority | Acceptance Criteria                                                                                                                                                  |
| ------- | -------------------------------------------------------------------------------------------------------------------------------------- | -------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| NFR-001 | The software architecture shall separate hardware access, application logic, diagnostic communication, and supervision services.       | High     | The codebase is organized into distinct modules or layers for BSP/drivers, application logic, diagnostic communication, and supervision/fault handling.              |
| NFR-002 | The system shall prioritize diagnostic observability over feature richness.                                                            | High     | During bench testing, system mode, actuator state, temperature, reset cause, and active fault information are observable through CAN messages or snapshot responses. |
| NFR-003 | The diagnostic communication shall remain available during degraded operation whenever the system is still powered and running.        | High     | In DEGRADED mode, heartbeat and status/fault CAN frames continue to be emitted unless the system resets or loses power.                                              |
| NFR-004 | The system shall support reproducible bench testing with DiagPack CAN.                                                                 | High     | At least 3 predefined test scenarios can be executed repeatedly with the same expected CAN-level observations.                                                       |
| NFR-005 | The project documentation shall be sufficient to reproduce the setup, test the main scenarios, and understand the diagnostic behavior. | Medium   | The repository includes at least a setup guide, CAN message description, fault list, and bench test procedure for the main scenarios.                                |
